# 原型需求理解与生成流程

更新时间：2026-08-13

## 目标

用户只需选择平台和单页/多页，然后用自然语言描述想要的原型。系统不得要求用户先理解或选择固定的“页面形态”“素材模式”。

系统应当：

1. 先理解用户真正想看到的画面和交互。
2. 已明确的要求不重复提问。
3. 只有会显著改变最终画面的关键缺口才提问，最多 3 题。
4. 每道题和选项根据本次需求动态生成，并提供自定义输入。
5. 用户确认后，将完整生成简报继续传给原型生成模型。

## 当前链路

```text
功能描述 + 平台 + 单页/多页 + 是否有参考图
              |
              v
POST /api/prototype/clarify
              |
              v
AI 提取已确认事实、构图、主体、动作、禁止项
       |                    |
 信息足够                   存在关键缺口
       |                    |
 直接生成              动态问题卡（最多 3 题）
       |                    |
       +-------- 用户确认 --+
              |
              v
generationBrief + “问题 -> 答案” + 原始描述
              |
              v
POST /api/prototype/generate
```

## 澄清接口

`POST /api/prototype/clarify`

请求：

```json
{
  "description": "做一个精灵展示页，星耀背景铺满，精灵居中，头顶打光，下方只有一个领取按钮",
  "platform": "APP",
  "hasReferenceImage": false
}
```

当信息已足够时：

```json
{
  "needsClarification": false,
  "intentSummary": "沉浸式精灵领取展示页",
  "generationBrief": "APP 单页；星耀背景铺满；人形精灵居中；顶部一束光照亮精灵；精灵下方仅一个领取按钮；禁止导航、说明卡片、属性数值和长文案。",
  "questions": []
}
```

当确实存在关键缺口时，`questions` 由 AI 根据本次需求生成。例如用户只说“获取人形精灵的展示页”，可以询问具体背景氛围；不再固定询问“完整页面/弹窗/局部模块”。

每道题包含：

- `id`：本次问题的语义标识
- `title`：短标题
- `prompt`：具体问题
- `options`：2~4 个针对本次需求的选项
- `allowCustomInput`：始终允许用户自行补充
- `customInputPlaceholder`：与本题相关的输入提示

## 生成约束

`generationBrief` 是澄清阶段形成的内部执行简报，前端不要求用户编辑，但必须原样提交给 `/api/prototype/generate`。

生成 prompt 的优先级：

1. 用户原始描述中的明确构图、数量、位置和禁止项
2. 用户对动态问题的确认答案
3. `generationBrief` 中提取的结构意图
4. 平台交互规范与组件尺寸
5. 默认视觉风格

组件库继续负责标准按钮、输入框、列表、表格和卡片的稳定样式。沉浸式展示页、角色主视觉、活动视觉和商品特写允许使用场景专用布局与局部 CSS，不能为了套组件库退化成普通卡片页。

用户未要求的导航、说明卡片、属性数值、统计数据、长文案和装饰图标不得自动添加。

## AI 修改策略

原型预览中的“让 AI 修改”分两条路径：

- 实时 patch：颜色、字号、文字、间距、圆角等局部调整，继续逐条作用到 iframe。
- 结构重构：重新布局、背景铺满、主体居中、只保留某些元素、删除多余模块、改成沉浸式画面等要求，直接生成完整的新 HTML。

结构性修改不能强制拆成零散 CSS patch，否则常出现只改了一部分、选择器匹配不到或旧结构仍然保留的问题。

## 异常降级

若澄清模型调用或 JSON 解析失败，系统不会阻断生成，也不会回到固定问题题库。后端会生成保守简报：忠实执行原始描述，仅补齐基本可用性，不增加未要求的业务模块。降级简报同样会执行关键词兜底：描述命中壁纸、角色主视觉、精灵、商品图等视觉依赖关键词时，仍会生成 `assetPlan`；多页面需求再按锁屏/主屏/组件/充电等已确认页面拆分 `assetPlans`，避免澄清超时导致整套页面完全无图。

需求分析和答案汇总使用独立的轻量请求策略，不继承正式原型生成的高推理开销：推理强度固定为 `low`，最大输出为 `4096` tokens，整体调用预算为 90 秒，不执行网络重试，也不切换备用 wire format。正式 HTML 原型生成仍沿用用户配置的模型、推理强度、输出上限和流式链路。中转站连接异常时，需求分析会在单次预算结束后立即使用保守简报继续，不再因三轮重试占满前端等待时间。

## 素材生成扩展

## 核心流程

1. 前端提交功能描述、平台和是否有风格参考图。
2. 后端调用需求分析模型，提取已确认构图，并决定是否需要补问，最多返回 3 个与本次需求直接相关的问题。
3. 同一次分析会生成内部 `assetPlan`。该字段不会在页面上显示为“素材模式”，前端只负责随生成请求原样带回。
4. 普通后台、表单、列表和纯结构页面不生成图片；人物、精灵、商品特写、活动主视觉等没有主体图片就无法成立的页面，最多生成 1 张核心素材。
5. 上传参考图默认仅覆盖视觉风格。只有用户明确要求“使用上传图片作为主体/实际素材”时，才把上传图嵌入页面。
6. 需要新素材时，后端先调用独立 Image API，再把固定占位符交给 HTML 模型。HTML 返回后由后端替换成图片 Data URL，模型不能编造图片地址。
7. 图片生成失败不会令原型任务失败，系统会继续生成可编辑的无图片版本。

## Flintic 图片配置

图片生成使用独立接口 `POST /v1/images/generations`，默认模型为已验证可用的 `gpt-image-2`，不复用 `gpt-5.5` Responses 的文本响应解析。

```text
AI_IMAGE_ENABLED=true
AI_IMAGE_BASE_URL=https://api.flintic.uk
AI_IMAGE_API_KEY=<Flintic API Key>
AI_IMAGE_MODEL=gpt-image-2
AI_IMAGE_QUALITY=medium
AI_IMAGE_TIMEOUT_SECONDS=180
```

`AI_IMAGE_BASE_URL` 和 `AI_IMAGE_API_KEY` 未单独填写时，会回退到当前用户已启用的 `ai_model_config`。推荐部署时单独设置环境变量，使所有用户共享后端图片能力且不向浏览器暴露 Key。

## 数据存储

- 本次改造不需要新增数据库表或 SQL。
- 生成图片由 `FileStorage` 保存。
- `prototype_result.reference_image_url` 记录生成文件的服务端存储路径。
- HTML 中使用 Data URL，因此预览与单文件 HTML 导出不依赖本地磁盘 URL，也不需要对象存储。

## 2026-08-13 流程优化

### 用户回答后的最终规划

当澄清接口返回问题时，前端收集答案后先调用：

```text
POST /api/prototype/clarify/finalize
```

后端会重新合并原始描述、初步简报和最新答案，覆盖初步 `generationBrief`、`assetPlan` 与 `assetPlans`。最终规划不再提问，并重新决定是否生图、素材来源、图片比例和透明背景。若最终规划调用失败，则保留初步素材计划，并把用户答案作为高优先级约束追加到简报。

### HTML 流式生成与图片串行组装

最终规划完成后，原型任务按以下顺序执行：

```text
HTML 流式生成 ─ 图片 1 ─ 图片 2 ─ 图片 3 ─ 合并素材 ─ 质量守卫 ─ 保存结果
```

- HTML 仍沿用原有 SSE 流式输出，并且最先执行，避免文本生成与图片生成争抢同一个中转站 Key 的并发额度。若仍受到外部请求影响并返回并发限制，按 5 秒、10 秒退避，最多尝试 3 次。
- HTML 完成后，多张图片按页面顺序逐张生成；单张图片遇到并发额度限制时按 3 秒、6 秒退避，最多尝试 3 次。
- 图片接口失败或超时仍只降级对应页面，不影响已经生成的 HTML 和其他页面图片。
- 单页面继续使用兼容字段 `assetPlan`，原有调用方式不变。
- 多页面使用 `assetPlans` 规划页面独立素材，最多 3 项；图片逐张执行，一项失败只清理对应页面的占位符，不影响其他页面。
- 每项素材通过稳定的 `key` 和目标页标题 `targetPage` 绑定页面，占位符格式为 `__PROTOTYPE_ASSET_<key>__`；旧占位符 `__PROTOTYPE_PRIMARY_ASSET__` 继续兼容。

### 确定性质量守卫

模型结果清洗后进入 `PrototypeQualityGuard`。它只修复能从最终简报中明确判断的问题：

- 替换图片占位符；模型漏放图片时自动补入核心主体图。
- 图片失败时清理残留占位符。
- 明确禁止导航时，移除导航、侧栏和底部 TabBar 结构。
- 明确要求只有一个按钮时，仅保留页面标记中的第一个按钮，不改动 `<script>` 内模板字符串。
- 注入按钮文字居中、图片最大宽度、移动端横向溢出兜底样式。
- 多页面 JSON 无法解析时保留原内容并记录警告，不做破坏性重写。

质量守卫不会根据模糊描述重排页面，也不会再次调用 AI，因此不会形成无限修复循环。
## 图片透明背景与预览高度

- 需要独立主体素材时，图片服务使用纯色色键背景生成，并在服务端转换为真实 PNG Alpha；不再信任模型绘制的“透明棋盘格”。
- 如果返回图片无法可靠识别色键背景，系统保留原始不透明图片继续生成页面，不再因为抠图失败丢弃整张素材；若模型直接绘制棋盘格，该网格仍可能留在原图中，因此提示词继续强制要求纯色色键背景。
- APP/PAD 预览首次使用设备尺寸加载，加载完成后改为按 iframe 实际内容高度展示；短页面紧凑结束，长页面由中间画布滚动。
- 普通移动页面禁止固定 `844px` 或 `100vh`。只有明确的锁屏、壁纸或完整手机屏幕允许使用固定设备高度，且内容需要合理填满画布。
- 多页面不会机械变成登录/首页/详情/设置；页面集合由用户需求决定。视觉需求明确依赖图片时，最终规划不得把已有素材计划降级为 `NONE`。
- 多页面壁纸、主题和角色展示需求可为锁屏页、桌面页、组件页、充电页分别规划图片，不再要求所有页面共用首图。
- 视觉成立依赖图片的需求不会因最终规划波动被降级为 `NONE`；若最终规划错误清空素材，系统会恢复有效的初步素材计划。
- `prototype_result.reference_image_url` 仍只记录第一张生成图的存储路径，各页面实际图片以内嵌 Data URL 保存在对应 HTML 中。
- 此次多素材扩展不新增数据库字段，不需要执行 SQL。
