# 策划部 AI 辅助设计平台 — 技术选型方案（Vue + SpringBoot + MySQL 版）

> 前提：内部正式系统（长期维护）、10~15人规模、第三方大模型API、账号自注册无权限分级、PC端

---

## 一、选型总原则

10~15 人用户量级，**任何"为了未来扩展"而引入的复杂度都是负资产**。选型优先级：
1. 团队维护成本低（成熟生态、文档全、招人/交接容易）
2. 能自然承接"调用大模型 + 长耗时异步任务"这个核心场景
3. 不做过度设计（不上微服务、不上K8s、不上复杂消息中间件集群）

---

## 三、分层选型明细

### 1. 前端

| 项 | 推荐 | 理由 |
|---|---|---|
| 框架 | **Vue3 + TypeScript** | 已确定 |
| UI组件库 | **Element Plus** | 现成的表单、上传、列表、进度条组件，能覆盖你页面清单里90%的交互，不需要自己造轮子；企业内部管理系统场景下与Element Plus的设计语言天然契合 |
| 状态管理 | **Pinia** + **Vue Query (TanStack Query)** | Pinia管全局状态（如用户登录态），Vue Query专门管"服务端数据"——这个系统几乎所有数据都来自后端异步任务，用它能天然处理轮询、缓存、loading态，比自己手写状态机省事很多 |
| 长任务反馈 | **SSE（Server-Sent Events）** 或轮询 | PRD生成/原型生成是耗时操作，需要前端展示"分阶段进度"（P0页面里明确要求了）。SSE比WebSocket轻量，比轮询实时，适合"只需服务端推进度、不需双向通信"的场景；Spring Boot原生支持`SseEmitter`，实现成本很低 |

### 2. 后端

| 项 | 推荐 | 理由 |
|---|---|---|
| 语言/框架 | **Java + Spring Boot** | 已确定。配套用 **Spring Web + Spring Data JPA + Spring Security（仅用其JWT/密码加密能力，不启用复杂RBAC）** |
| 异步任务 | **`@Async` + 线程池** | PRD生成/原型生成/PRD审查都是"提交任务→后台跑→轮询或SSE推送结果"模式。10~15人量级、并发量很低，`@Async`+自定义线程池完全够用，**不需要引入RabbitMQ/Kafka这类消息队列**——这是最容易被"过度设计"的一环，量级到之前没必要上 |
| 任务状态存储 | Redis（可选）或直接MySQL一张`task`表 | 任务量小的情况下，甚至可以不引入Redis，直接用MySQL的一张任务状态表（`pending/running/success/failed`）+ 轮询查询即可，进一步简化技术栈。如果后续任务量上来了，再引入Redis做状态缓存 |
| 鉴权 | **Spring Security + JWT + BCryptPasswordEncoder** | 无权限分级，不需要完整RBAC框架，简单的"注册-登录-签发token-拦截器校验"即可 |

> **关于要不要保留Redis**：如果你想尽量精简技术栈（团队人少、要长期自己维护），**第一版可以先不引入Redis**，任务状态和缓存都用MySQL扛，后续真的有性能瓶颈了再加。这是给你的一个可以进一步简化的选项。

### 3. 数据存储

| 项 | 推荐 | 理由 |
|---|---|---|
| 数据库 | **MySQL 8.0+** | 已确定。MySQL 8.0的JSON字段类型已经支持基本的JSON查询和虚拟列索引，配合你的PRD结构化数据（用JSON列存章节内容）基本够用；且Java/SpringBoot生态里MySQL的成熟度、团队熟悉度、运维资料都更充分，符合"团队会不会踩坑"优先的原则 |
| 文件存储 | **对象存储**（内网可用MinIO自建，云上用阿里云OSS/腾讯云COS） | 存放用户上传的XMind/Word原件、生成的原型图/导出文件。不要把文件塞进数据库或服务器本地磁盘，长期维护会很痛苦（备份、扩容、迁移都麻烦） |

### 4. AI集成层（这是本项目技术难度最高的部分，单独说明）

| 能力 | 技术方案 | 备注 |
|---|---|---|
| PRD生成/增强/审查 | 后端通过`RestTemplate`/`WebClient`调用大模型API，做prompt模板管理 | 相对标准，用Claude/GPT的API即可，重点在prompt工程质量而非架构复杂度。`WebClient`（Spring WebFlux）比传统`RestTemplate`更适合调用大模型这种"响应慢、可能要流式输出"的接口 |
| XMind解析 | XMind文件本质是zip压缩包，内部是content.json（新版）或content.xml（旧版）| 后端用Java的`java.util.zip`解压+解析（或引入`Jackson`解析JSON部分），转成结构化大纲文本后再喂给大模型 |
| **原型图生成** | 让大模型直接生成 **HTML/CSS（或前端组件代码）**，前端用 `iframe` 沙箱渲染 | ⚠️ 这是四个模块里技术风险最高的一个：文字描述→可交互原型，本质是"text-to-UI代码生成"。建议先用Claude这类擅长写前端代码的模型做技术验证（POC），确认生成质量能满足预期后再投入正式开发，避免这个模块拖慢整体上线时间 |
| Word导出 | **Apache POI** | Java生态生成Word文档的标准库，把结构化PRD数据渲染成docx，成熟方案 |

## 四、部署方案

- **容器化**：Docker + Docker Compose，把前端、后端(Spring Boot打成jar包)、MySQL 三/四个服务编排在一起，一条命令启停，适合小团队自己运维
- **不建议**：K8s、微服务拆分、多环境复杂CI/CD——10几人用的内部系统，这些都是维护负担而非价值
- **建议保留**：一个简单的CI（比如GitHub Actions/GitLab CI跑一下`mvn test`+构建镜像），这个成本很低但能避免"改一行代码手动上传服务器"的原始操作

## 五、和上一版（Python技术栈）的主要差异对照

| 层 | 上一版（Python） | 本版（Java/SpringBoot） |
|---|---|---|
| 后端框架 | FastAPI | Spring Boot |
| 异步任务 | Celery + Redis | `@Async`线程池（Redis可选，非必需） |
| 数据库 | PostgreSQL | MySQL |
| Word导出 | python-docx | Apache POI |
| AI调用 | Python HTTP客户端 | `WebClient`(Spring WebFlux) |

核心结论不变：技术栈本身不是这个项目的风险点，**唯一有不确定性的是"原型图生成"模块**，仍然建议单独花1~2天做技术验证再排入正式开发计划。

---

## 六、给你的一个待确认点

**要不要在第一版就引入Redis？** 我的建议是**先不引入**——用一张MySQL任务状态表+轮询就能支撑10~15人的使用量，技术栈越精简，团队长期维护成本越低。如果后续真的遇到性能瓶颈（比如任务量暴增、轮询压力大），再加Redis也不迟，不会有大的重构成本。
